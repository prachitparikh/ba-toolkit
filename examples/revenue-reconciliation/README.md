# Revenue reconciliation: finding the gap between a dashboard and the ledger

This is the working version of my video [Dashboard Numbers Don't Match? Find the Gap in SQL](https://www.youtube.com/watch?v=SG-6rtZeizg). The video walks through the method. This folder has the data, the SQL and the tests, so you can run it yourself and get the same numbers.

The setup: for October 2026, finance reports **$1,236,200** in revenue and the revenue dashboard shows **$1,284,500**. That's a **$48,300** gap. "The dashboard is wrong" doesn't help anyone. What does help is a bridge: a short list of causes, each with an amount and its own query, that takes you from one number to the other with nothing left over.

> **Northstar Systems is a fictional client.** All the data here is generated by `generate_data.py`, and the four problems are planted on purpose so the SQL has something real to find. None of it comes from a real company.

## The bridge

| Step | Amount | Running total |
|---|---:|---:|
| Finance ledger revenue (completed orders, US Eastern date) | 1,236,200 | 1,236,200 |
| 1. Cancelled orders still counted on the dashboard | +9,600 | 1,245,800 |
| 2. Time-zone cutoff (dashboard uses UTC, finance uses US Eastern) | +4,200 | 1,250,000 |
| 3. JOIN fan-out on `order_promotions` (double counting) | +41,900 | 1,291,900 |
| 4. Orphan orders dropped by the INNER JOIN to `customers` | -7,400 | 1,284,500 |
| **Revenue dashboard** | **1,284,500** | **1,284,500** |

Unexplained difference: **0.00**. That last line is the one that matters. If it isn't zero, the job isn't finished.

**See it as a dashboard:** [Dashboard vs finance revenue reconciliation on Tableau Public](https://public.tableau.com/app/profile/prachit.parikh/viz/DashboardvsFinanceRevenueReconciliationinSQLPrachitParikh/RevenueReconciliation). The bridge, the daily ledger against the dashboard, and the daily gap split by cause, built from this folder's `output/` files.

## What each step means

1. **Cancelled orders.** Finance only books completed orders. The dashboard query has no status filter, so six cancelled orders spread across the month get counted anyway.
2. **Time-zone cutoff.** Finance books each order on its US Eastern date. The dashboard groups by the UTC date. An order placed at 9 pm Eastern on Sep 30 is already Oct 1 in UTC, so the dashboard counts it in October (+10,500). An order placed at 9 pm Eastern on Oct 31 is Nov 1 in UTC, so the dashboard misses it (-6,300). Net: +4,200.
3. **JOIN fan-out.** The dashboard joins orders to `order_promotions` so people can filter by promo code. Some orders have two, three or four promotion rows. After the join, the order shows up once per row and `SUM(amount)` adds the full order amount each time. This is the biggest piece of the gap, and it's the easiest one to miss because every row in the result looks correct on its own.
4. **Orphan orders.** Five completed orders point at a `customer_id` that isn't in the customers table. Finance still counts them because the revenue is real. The dashboard's INNER JOIN to customers drops them without any warning, which pulls the dashboard down by 7,400.

Two of the problems push the dashboard up and one pulls it down. If you only look at the net gap you can't see that, which is why each component gets its own query.

## How to run it

You need Python 3.9 or later. The scripts use only the standard library. The tests need `pytest`.

```bash
cd examples/revenue-reconciliation
python generate_data.py && python run.py && pytest
```

- `generate_data.py` writes the CSVs in `data/`. The seed is fixed, so you get the same files every time.
- `run.py` loads the CSVs into an in-memory SQLite database, runs `reconcile.sql`, prints the bridge and writes the files in `output/`.
- `pytest` checks every number in the bridge, checks that it balances to the cent, and checks that the daily file adds up to the monthly totals.

The data and output files are committed too, so you can open the CSVs on GitHub without running anything.

| [`output/bridge.csv`](output/bridge.csv) | The bridge: `step_order, step, amount, running_total` |

In `daily.csv`, finance is booked on the Eastern date and the dashboard on the UTC date. Each component sits on the day it affects, so on every row `finance_revenue + cancelled + timezone + fanout + orphans = dashboard_revenue`. The time-zone effect only shows up on Oct 1 and Oct 31, which is what you'd expect from a cutoff problem. The other three are spread across the month.

## Using this on your own data

The structure carries over to any "two reports disagree" problem:

1. Write down the rule each side uses: which records, which date, which time zone, which joins.
2. Write the second report's query exactly as it is today, bugs and all.
3. Give each difference you suspect its own query and its own amount.
4. Add a check that the starting number plus every component equals the ending number. Keep digging until the unexplained amount is zero.

The SQL here is SQLite. The time-zone handling is a simple offset rule that only covers this data window. In a real warehouse, use its time-zone function instead (`AT TIME ZONE` in PostgreSQL and SQL Server, `CONVERT_TIMEZONE` in Snowflake and Redshift).
